# proton-mcp: run, deploy, operate

Operational runbook for `proton_email_server.py` — a single-file Python MCP server exposing
Proton Mail as 5 tools. This skill covers how to run it, where it runs in production, every
configuration knob, and how to ship changes to both deployments.

Facts marked "as of 2026-07-02" were verified on that date; re-check with the commands in
"Provenance and maintenance" before relying on them.

## Jargon (defined once)

| Term | Meaning |
|---|---|
| MCP | Model Context Protocol — how AI clients (Claude Code, LibreChat) call external tools. |
| stdio transport | MCP over the process's stdin/stdout. The client (Claude Code) launches the server as a child process and speaks JSON-RPC over pipes. No network port. |
| streamable-http | MCP over HTTP. The server runs standalone (here via uvicorn on port 3004) and clients connect to `http://host:3004/mcp`. |
| Proton Bridge | Proton's official desktop app that logs into Proton Mail and re-exposes the mailbox as local plaintext-ish IMAP (1143) and SMTP (1025). This server talks to the Bridge, never to Proton's servers directly. The Bridge password is an app password generated by the Bridge, NOT the Proton account password. |
| LibreChat | Self-hosted chat UI on the desktop that consumes this server as an MCP tool provider over streamable-http. |

## Configuration reference (this skill owns this table)

The server reads configuration ONLY from the process environment (`os.environ.get`, lines
29–33 and 333–339 of `proton_email_server.py`). **It never loads `.env`** — `python-dotenv` is
in requirements.txt but never imported. Env must come from the launcher: `~/.claude.json` on
the Mac, container env on the desktop, or your shell for manual runs.

All values below as of 2026-07-02. Never copy credential values or the Proton account email
address into any file — reference locations only.

| Var | Code default | Mac stdio actual | Desktop container actual |
|---|---|---|---|
| `PROTON_USERNAME` | `""` | set in `~/.claude.json` (do NOT copy value) | set in container env |
| `PROTON_PASSWORD` | `""` | set in `~/.claude.json` (Bridge app password, NOT the account password) | set in container env |
| `PROTON_BRIDGE_HOST` | `127.0.0.1` | `10.0.0.243` | `localhost` (host networking) |
| `PROTON_BRIDGE_IMAP_PORT` | `1143` | `1143` | `1143` |
| `PROTON_BRIDGE_SMTP_PORT` | `1025` | `1025` | `1025` |
| `MCP_TRANSPORT` | `stdio` | (unset → stdio) | `streamable-http` |
| `MCP_HOST` | `0.0.0.0` | n/a (stdio) | `0.0.0.0` |
| `MCP_PORT` | `3004` | n/a (stdio) | `3004` |

**TRAP — `.env.example` vs reality:** the template says `PROTON_BRIDGE_HOST=127.0.0.1`, but the
real Mac deployment points at `10.0.0.243` (Bridge runs on the desktop, not the Mac). The
template is a template, not a record of deployment. This has confused sessions before. When in
doubt, the deployment configs (`~/.claude.json`, container env) are the truth.

The Dockerfile bakes in `MCP_TRANSPORT=streamable-http`, `MCP_HOST=0.0.0.0`, `MCP_PORT=3004`
and `EXPOSE 3004`; credentials and `PROTON_BRIDGE_HOST` come from the container's runtime env.

Credential locations (values live here and ONLY here):

- Mac: `~/.claude.json` under `mcpServers["proton-mail"].env`
- Desktop: `proton-email-mcp` container env (visible via `docker inspect`)
- Bridge state/auth: volume `/opt/docker/auth-stack/data/protonmail-bridge`

### Adding a new env var

Any new env var is a behavior-affecting change — route it through `proton-mcp-change-control`
first. Then:

1. Read it in code with `os.environ.get("NEW_VAR", "<default>")` next to the existing config
   block (lines 29–33). Module-level config is read at import time — tests must set env
   BEFORE importing the module (see `proton-mcp-validation-and-qa`).
2. Add it to `.env.example` with the code default and a comment.
3. If the desktop container needs a baked default, add `ENV NEW_VAR=...` to `Dockerfile`.
4. Update BOTH deployment configs: `~/.claude.json` env block (Mac) and the desktop container
   env (via the redeploy procedure below).
5. Re-verify both deployments (Provenance section) and update the table above.

## Run locally (Mac)

### stdio smoke test

```bash
cd /Users/prestonbernstein/dev/proton-email-mcp && MCP_TRANSPORT=stdio ./venv/bin/python proton_email_server.py
```

Expected: a startup log line on stderr ("Starting Proton Bridge Email MCP server...") and, if
creds are unset in your shell, warnings `PROTON_USERNAME not set` / `PROTON_PASSWORD not set`
(warnings only — the server still starts; tools return "❌ Error: Proton credentials not
configured" strings instead of raising). The process then waits silently for MCP JSON-RPC on
stdin. Ctrl-C to stop. This proves imports, FastMCP construction, and startup — it does not
touch the Bridge.

### streamable-http locally

```bash
cd /Users/prestonbernstein/dev/proton-email-mcp && MCP_TRANSPORT=streamable-http MCP_PORT=3004 ./venv/bin/python proton_email_server.py
```

Expected: uvicorn startup logs, listening on `0.0.0.0:3004`. Probe from another terminal:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3004/mcp
```

Any HTTP status (not connection-refused) means the app is up — the MCP endpoint requires a
proper MCP handshake, so a plain GET returning 4xx is normal. Ctrl-C to stop. Don't leave this
running: it is unauthenticated.

To exercise Bridge connectivity from a manual run you'd also need
`PROTON_BRIDGE_HOST=10.0.0.243` and credentials in the environment — prefer the read-only
smoke scripts in `proton-mcp-diagnostics-and-tooling` instead of hand-exporting creds.

## Claude Code registration (Mac)

Lives in `~/.claude.json` → `mcpServers["proton-mail"]` (as of 2026-07-02):

- `command`: `/Users/prestonbernstein/dev/proton-email-mcp/venv/bin/python3.14`
- `args`: `["/Users/prestonbernstein/dev/proton-email-mcp/proton_email_server.py"]` (absolute path)
- `env`: `PROTON_USERNAME`, `PROTON_PASSWORD` (values live only in this file — never copy them
  out), plus `PROTON_BRIDGE_HOST=10.0.0.243`
- transport: stdio (no `MCP_TRANSPORT` needed; stdio is the code default)

Tools surface in sessions as `mcp__proton-mail__<tool>`, e.g. `mcp__proton-mail__list_folders`,
`mcp__proton-mail__read_recent_emails`, `mcp__proton-mail__search_emails`,
`mcp__proton-mail__send_email`, `mcp__proton-mail__get_email_stats`.

Editing `~/.claude.json` requires a Claude Code restart to take effect (ASSUMPTION — standard
Claude Code behavior; the server process is spawned at session start). Because the registration
points at the repo file path, source edits also take effect on the next restart with no other
deploy step.

Quick health check inside a session: call `mcp__proton-mail__list_folders` (read-only). If the
tools are missing entirely, check `~/.claude.json` syntax and restart; if they return
credential errors, check the env block; if they hang or return connection errors, the Bridge
or LAN path is the suspect — see `proton-mcp-debugging-playbook`.

### Proton Bridge container (`protonmail-bridge`)

Defined in `/opt/docker/auth-stack/docker-compose.yml` (verbatim from facts pack, 2026-07-02):
built from local `Dockerfile.bridge`, network `auth-net`, ports `1025:25` and `1143:143`,

means re-pairing the Bridge with the Proton account), `cap_add: SYS_PTRACE`, restart

Restart (UNVERIFIED exact invocation — standard compose pattern, not executed during fact
gathering):

```bash

```

Both MCP deployments break when the Bridge is down; check it first when both fail at once.

### LibreChat wiring

LibreChat lives at `/opt/docker/librechat-stack/`. Its `librechat.yaml` (as of 2026-07-02) has:

- `mcpServers.proton-email`: `url: http://localhost:3004/mcp`, `type: streamable-http`
- `mcpSettings.allowedDomains` including `http://localhost:3004`

The `allowedDomains` entry is REQUIRED: LibreChat's SSRF protection blocks MCP URLs on
localhost/private-LAN addresses unless explicitly allowlisted, and a missing entry silently
disables the server (no loud error — tools just never appear). If LibreChat can't see the
tools, check this before anything else, then restart LibreChat so it re-handshakes:

```bash
ssh desktop-agent 'cd /opt/docker/librechat-stack && sudo docker compose restart'
```

(UNVERIFIED exact invocation — standard compose pattern; the service name for a targeted
restart was not recorded, so this restarts the stack.)

## Redeploy procedure (behavior changes must ship to BOTH deployments)

Canonical source is the Mac repo. Workflow: edit on the Mac → tests pass
(`./venv/bin/python -m pytest tests/ -q`, expect 12 passed) → change-control gate cleared →
then ship to both targets. Shipping to only one target creates exactly the source drift this
project is trying to kill.

### Target A — Mac stdio

Nothing to copy: `~/.claude.json` launches the repo file directly. Restart Claude Code
(ASSUMPTION on restart requirement, see registration section above) and verify with a
read-only tool call (`mcp__proton-mail__list_folders`).

### Target B — desktop container

No deploy pipeline exists (as of 2026-07-02); this is manual. Steps marked (U) depend on the
UNVERIFIED launch method and require the discovery output first.

1. Discovery (mandatory, see above): `ssh desktop-agent 'sudo docker inspect proton-email-mcp'`
   — save the env and run config before destroying anything.
2. Copy source from the Mac repo to the designated desktop build context:
   `/opt/docker/librechat-stack/proton-email-mcp` — the copy that matched canonical when
   drift was measured 2026-07-02 and the build context designated by
   `proton-mcp-drift-and-hardening-campaign` (Phase A2). Do NOT build from
   `/home/preston/docker/proton-email-mcp` — measured stale (pre-fix snapshot) on 2026-07-02.

   ```bash
   scp /Users/prestonbernstein/dev/proton-email-mcp/proton_email_server.py \
       /Users/prestonbernstein/dev/proton-email-mcp/requirements.txt \
       /Users/prestonbernstein/dev/proton-email-mcp/Dockerfile \
       desktop-agent:proton-email-mcp-staging/
   ssh desktop-agent 'sudo cp ~/proton-email-mcp-staging/* /opt/docker/librechat-stack/proton-email-mcp/ && rm -rf ~/proton-email-mcp-staging'
   ```

   (Staging via the agent home because `/opt/docker/` writability for the agent user is
   UNVERIFIED; `sudo cp` covers it.)
3. Build: `ssh desktop-agent 'sudo docker build -t proton-email-mcp:latest /opt/docker/librechat-stack/proton-email-mcp'`
4. (U) Replace the container, re-using the EXACT env and flags from step 1:

   ```bash
   ssh desktop-agent 'sudo docker stop proton-email-mcp && sudo docker rm proton-email-mcp'
   # then docker run with: --name proton-email-mcp --network host --restart always
   # and -e flags reproducing the inspected Config.Env (credentials included — from
   # the inspect output, never from this document)
   ```

5. Verify the port: `ssh desktop-agent 'sudo ss -tlnp | grep 3004'` and check container logs
   for the uvicorn startup line.
6. Restart LibreChat (see above) so it re-handshakes and re-lists the tools.
7. Verify end-to-end with a read-only tool call from LibreChat, or the smoke scripts in
   `proton-mcp-diagnostics-and-tooling`.

After any redeploy, re-run the drift check (`proton-mcp-diagnostics-and-tooling`) to confirm
the three source copies now match; the longer-term fix for this whole manual dance is tracked
in `proton-mcp-drift-and-hardening-campaign`.

## Safety rules for live operation

- Any live test that SENDS email requires explicit human confirmation first, and during
  dev/test send only to the account's own address (ASSUMPTION, coordinator-sanctioned — no
  repo doc states it, but treat as binding).
- Read-only operations are acceptable for verification without confirmation: `list_folders`,
  `get_email_stats`, `read_recent_emails`, `search_emails`.
- Never write credential values or the Proton account email address into any file, log, doc,
  or skill — reference the three credential locations by path only.
- Don't leave a local streamable-http instance running on the Mac; it is unauthenticated.
